01 Reducción de llamadas de red

Casos donde se puede reutilizar un dato ya obtenido en vez de volver a golpear un servidor.
Alta

Dos hooks distintos piden las stars del mismo repo a la API de GitHub

useGitHubStars.ts / useRepoStats.ts

useGitHubStars y useRepoStats hacen esencialmente lo mismo: extraen owner/repo de una URL, llaman a api.github.com/repos/{owner}/{repo}, y cachean el resultado en sessionStorage con la misma duración (1h). useRepoStats es un superset (también soporta GitLab y GitLab-GNOME).

Verificado en el grafo de código

useGitHubStars no tiene ningún import en src/ — es código muerto que sigue disparando llamadas si algo lo vuelve a usar, y duplica lógica de parseo de URL y caché que ya vive en useRepoStats.

Acción

Eliminar useGitHubStars.ts. Extraer el fetch a GitHub/GitLab de useRepoStats a un servicio compartido (services/repoStats.ts) para no repetir la lógica de caché de sessionStorage.

Alta

React Query sin staleTime: refetch en cada montaje de página

router.tsx · useCategoryApps.ts · useDeveloperApps.ts

router.tsx crea new QueryClient() sin defaultOptions. Con el default de React Query (staleTime: 0), cualquier useQuery sin staleTime propio se considera obsoleto de inmediato y vuelve a pedir datos al servidor cada vez que el componente se monta — incluso si el usuario solo está navegando entre una categoría y volviendo atrás.

Afectados directamente

useCategoryApps y useDeveloperApps no definen staleTime: cada visita a /category/:id o /developer/:id repite la búsqueda en Algolia/Meilisearch aunque los datos no hayan cambiado en meses.

Acción
export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 5 * 60_000,   // 5 min por defecto
      gcTime: 30 * 60_000,
    },
  },
});

Los hooks que ya tienen caché SQLite propia (useAppOfTheDay, useCategories, etc.) no se ven afectados porque controlan enabled manualmente.

Media

N+1: getCategoryApp se llama una vez por app para reconstruir "app del día" y "de la semana"

useAppOfTheDay.ts · useAppsOfTheWeek.ts

apiService.getAppOfTheDay() devuelve solo un app_id; el hook hace un segundo POST a /search (getCategoryApp) para completar nombre/ícono/descripción. En useAppsOfTheWeek esto se repite una vez por cada app de la semana dentro de un Promise.all — típicamente 5-7 requests POST adicionales en cada refresh diario.

Acción

Si el backend de búsqueda soporta filters por app_id con múltiples valores (OR), agrupar todos los app_id de la semana en una sola llamada a /search en vez de N llamadas individuales — el mismo patrón que ya usa getDeveloperApps con filterType: "developer_name".

Media

useAppScreenshots sondea hasta 10 claves de caché en serie de forma optimista

useAppScreenshots.ts

Genera 10 claves ({appId}:::1 … :::10) y las resuelve con Promise.all, pero corta en el primer hueco. Si una app solo tiene 3 screenshots cacheados, igual se disparan 10 invocaciones IPC a Rust (get_cached_image_info) en paralelo — 7 de ellas garantizado que fallan.

Acción

El AppStream ya trae screenshots.length antes de cachear; guardar ese conteo en la fila de la tabla de caché (o en el nombre de archivo) evita adivinar cuántas claves probar.

Baja

Deduplicación de requests solo cubre GET/POST idénticos en vuelo simultáneo

apiClient.ts

Buena señal: ApiClient.request ya deduplica llamadas concurrentes idénticas vía pendingRequests. Lo que falta es una capa de caché temporal en memoria (TTL corto, ej. 30s) para respuestas ya resueltas — hoy dos componentes que piden lo mismo con 200ms de diferencia (no simultáneos) generan dos llamadas HTTP reales.

Acción

Ya que ApiClient es la única puerta de salida (fan-in 34), es el lugar correcto para un cache-aside con TTL corto en vez de resolverlo hook por hook.

02 Arquitectura de componentes

Patrones repetidos que conviene consolidar en una sola instancia/abstracción.
Media

Seis modales con estructura y controles duplicados

AboutModal · DonationModal · ReleaseNotesModal · UpdateAllModal · LocalFlatpakInstallModal · SettingsModal

6 componentes de src/components (de 6.120 líneas totales) implementan su propio Dialog de MUI con header, botón de cierre, y padding, en vez de compartir un BaseModal. Esto no afecta llamadas de red, pero sí duplica lógica de accesibilidad (foco, onClose, Escape) y hace que un cambio de estilo (ej. radio de borde, transición) haya que aplicarlo 6 veces.

Acción

Extraer un <AppModal title actions> que envuelva Dialog + DialogTitle + botón de cierre, y que los 6 modales existentes solo aporten el contenido.

Media

Lógica de fetch+caché+retry de imagen duplicada entre ImageCacheManager y CachedImage

imageCache.ts · CachedImage.tsx

ImageCacheManager ya es un singleton correcto (cola con prioridad, 6 descargas concurrentes, backoff exponencial). Pero CachedImage.tsx mantiene su propio failedImagesCache y loadedImagesCache a nivel de módulo, además de repetir la detección de "error temporal" (mismas 4 substrings que ya están en imageCache.ts) y su propio retry con retryCount.

Acción

Mover isTemporaryError a un export compartido; considerar que los dos mapas de caché en memoria vivan en un solo lugar (el manager) en vez de estar partidos entre el hook/componente y el singleton.

Baja

Buen uso de singleton en DBCacheManager e ImageCacheManager

dbCache.ts · imageCache.ts

A diferencia del hallazgo anterior, esto ya está bien resuelto: ambos son getInstance() con inicialización perezosa y memoizada (initPromise), evitando abrir la conexión SQLite o releer el directorio de caché más de una vez. Es el patrón a replicar cuando se consolide algo similar en el frontend.

Baja

AppDetails.tsx concentra demasiadas responsabilidades (1.508 líneas)

pages/appDetails/AppDetails.tsx

15 useState/useEffect en un solo componente: instalación, verificación de hash, countdown, dependencias, popover, screenshots. Es manejable hoy, pero cada nueva feature (como backups) tiende a añadirse aquí en vez de a un hook dedicado.

Acción

Extraer el flujo de instalación/verificación (startInstallation, handleForceContinue, clearCountdown — ya aparecen como cluster propio en el grafo de llamadas) a un hook useAppInstallFlow, siguiendo el mismo patrón que ya usan useUpdateApp / useUninstallApp.

03 Rendimiento

Mejoras de velocidad percibida o real mediante mejores técnicas, sin tocar arquitectura.
Media

cachePermissionsBatch inserta en SQLite de a uno, en un loop await

dbCache.ts:496-504

El comentario en el código dice "no transaction to avoid locks", pero el resultado es N round-trips secuenciales a SQLite (uno por app) en vez de una sola transacción — que en SQLite es tanto más rápida como más segura ante corte a mitad de escritura (deja el batch parcialmente escrito).

Acción

Envolver el loop en BEGIN/COMMIT explícito (el plugin tauri-plugin-sql soporta execute secuencial dentro de una transacción); con WAL mode los locks no deberían ser un problema real para escritura desde un solo proceso.

Media

Doble invoke para resolver el path de una imagen ya descargada

imageCache.ts:downloadImage

downloadImage hace download_and_cache_image y luego, con el filename resultante, un segundo invoke("get_cached_image_path") para obtener el path completo. Son dos viajes IPC Rust↔JS cuando el primer comando ya podría devolver el path absoluto directamente.

Acción

Hacer que download_and_cache_image devuelva el path completo en vez del filename — cambio pequeño en lib.rs que elimina un invoke por cada imagen nueva descargada.

Baja

IntersectionObserver se crea uno por instancia de CachedImage

CachedImage.tsx:52-76

En una grilla con 50-100 tarjetas (Home, MyApps, CategoryApps) esto son 50-100 observers independientes. El navegador lo tolera, pero un IntersectionObserver compartido con un Map de callbacks por elemento reduce el overhead de setup/GC, especialmente notable en el DataCube de Analytics si en algún momento usa miniaturas.

Acción

Solo vale la pena si se detecta jank real al hacer scroll rápido en listas largas; no es prioritario hoy.

Baja

Buen manejo de backoff exponencial y cancelación consistentes

apiClient.ts · imageCache.ts

Tanto ApiClient.executeWithRetry como ImageCacheManager.downloadImage usan el mismo patrón 500 * 2^attempt con AbortController propagado. Es consistente y correcto — vale la pena extraerlo a un helper withRetry(fn, { maxRetries, baseDelay, signal }) compartido, más por mantenibilidad que por performance.

04 Estrategia arquitectónica de fondo

La arquitectura actual funciona, pero tiene una tensión estructural que vale la pena nombrar.
Estructural

Dos sistemas de caché paralelos y sin coordinación: React Query vs. SQLite manual

dbCache.ts + hooks/use*.ts + router.tsx

Hoy conviven dos estrategias de invalidación distintas para el mismo problema (evitar refetch innecesario):

Patrón A — manual (mayoría de hooks)

Cada hook (useAppOfTheDay, useCategories, useAppsOfTheWeek) reimplementa: leer SQLite al montar → decidir shouldFetch → useQuery({ enabled: shouldFetch }) → escribir de vuelta a SQLite dentro del queryFn. Son ~30 líneas de boilerplate case por caso, repetidas 3 veces casi idénticas.

Patrón B — delegado (minoría de hooks)

useCategoryApps y useDeveloperApps confían enteramente en React Query, sin tocar SQLite. Más simple, pero pierde la persistencia entre reinicios de la app que sí tienen los otros.

Por qué importa

La inconsistencia hace que la política de "cuánto tiempo es válido un dato" viva en tres capas distintas (SQLite cache_metadata, sessionStorage para stars, y staleTime implícito de React Query) sin una sola fuente de verdad. Cada hook nuevo tiene que decidir de nuevo cuál patrón seguir.

Sugerencia

Usar el persister oficial de React Query (@tanstack/query-persist-client-core con un adapter a tauri-plugin-sql) para unificar ambas capas: React Query pasa a ser la única fuente de verdad de "¿tengo datos frescos?", y la persistencia a SQLite se vuelve un detalle de implementación del persister en vez de código repetido en cada hook. Esto colapsaría ~120 líneas duplicadas entre los 3 hooks afectados a una configuración central.

Estructural

lib.rs concentra 3.699 líneas y ~35 comandos Tauri sin separar por dominio

src-tauri/src/lib.rs

A diferencia de backup.rs, donations.rs y licensing/ (que ya están extraídos como módulos), el archivo lib.rs mezcla en un mismo archivo: caché de imágenes, instalación/desinstalación de Flatpak, extensiones, PTY/terminal interactiva, chequeo de updates de GitHub, y registro de todos los comandos. Es el archivo con más fan-out del proyecto.

Sugerencia

Aplicar el mismo patrón de módulo que ya se usó para backup.rs: separar en flatpak.rs (install/uninstall/update/list), image_cache.rs, extensions.rs y pty.rs, dejando lib.rs solo con el Builder de Tauri y el generate_handler!. Reduce el fan-out del hotspot y hace que cambios en, por ejemplo, la terminal PTY no obliguen a re-revisar el archivo completo de 3.700 líneas.

Estructural

El estado de "apps instaladas" se deriva invocando al CLI de Flatpak en cada hook que lo necesita

installedAppsStore.ts · useInstalledApps.ts · useAvailableUpdates.ts · useGitHubUpdates.ts

Existe un store de Zustand (installedAppsStore) que centraliza el estado, lo cual es correcto. Pero varios hooks (useAvailableUpdates, useGitHubUpdates) parecen re-derivar/mezclar resultados por su cuenta invocando comandos Rust (get_available_updates, check_github_updates) en useEffect propios en vez de a través de una única acción del store que orqueste "refrescar todo lo relacionado con actualizaciones".

Sugerencia

Mover la orquestación de "chequear updates (Flathub + GitHub) y fusionar resultados" a una acción única del store (installedAppsStore.refreshUpdates()), para que los componentes solo lean estado derivado y nunca disparen el invoke directamente. Hoy si dos componentes montan useGitHubUpdates a la vez, se duplica el chequeo de GitHub para las mismas apps.

05 Dependencias externas reemplazables por código propio

Casos donde una librería aporta menos de lo que cuesta en peso de bundle o superficie de API frente a una implementación propia acotada al caso de uso real.
Dependencia Uso real detectado Impacto Sugerencia
uuid (^13.0.0) Generación de IDs simples en cliente Bajo El entorno de Tauri corre sobre WebView2/WebKit modernos: crypto.randomUUID() es nativo del navegador (Baseline desde 2022) y elimina la dependencia por completo, cero código propio necesario.
qrcode.react + react-qr-code Dos librerías de QR distintas instaladas a la vez, presumiblemente para DonationModal Medio Aunque no es "reemplazo por código propio", esto es duplicación directa de dependencias: elegir una sola (qrcode.react es más mantenida) y remover la otra. Revisar antes de generalizar.
@react-three/fiber + @react-three/drei + three Un solo componente, DataCube.tsx en Analytics Bajo ~600KB+ de dependencias para una sola visualización 3D. Si DataCube es un cubo de bloques de color relativamente simple, evaluar si una implementación con Canvas 2D + CSS 3D transforms cubre el caso sin la carga de un motor WebGL completo. Si la app crece a más visualizaciones 3D, mantenerlo se justifica; hoy es 3 dependencias pesadas para 1 pantalla.
use-debounce Debounce de AppSearchBar probablemente Bajo Un debounce es ~10 líneas de useEffect + setTimeout. Reemplazar por un hook propio useDebouncedValue evita una dependencia entera por una utilidad trivial y ya usada en un único lugar.
Rust: xxhash-rust, zstd, tar Hashing y compresión en backup.rs / verificación de apps Mantener Estas sí están bien justificadas: implementar xxHash, zstd o el formato tar a mano sería un error de ingeniería (algoritmos no triviales, con implicancias de seguridad/corrección). No se sugiere reemplazo.
Nota general: el criterio aplicado fue "¿la librería resuelve un problema de dominio complejo (compresión, criptografía, parsing) o un problema trivial (UUID, debounce) que el propio JS/Web API moderno ya resuelve?". Solo se marcan como candidatas a reemplazo las del segundo grupo — no se sugiere tocar nada de MUI, Zustand, TanStack Router/Query ni las libs de Tauri, que están justificadamente integradas en profundidad.
